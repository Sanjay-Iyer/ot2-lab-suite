# Understanding the Protocol

`protocols/dilution_protocol.py` is the file the Opentrons simulator (or
a real OT-2) actually executes. This guide explains what it does and how
the volume math works, without requiring you to read the source code.

## Protocol stages

The protocol runs four stages in order. If any stage fails, everything
stops before any liquid handling begins.

### 1. Load config

The protocol reads the YAML config from one of two sources (checked in
this order):

1. The `OT_CONFIG_PATH` environment variable.
2. A hardcoded fallback path (`configs/example_experiment.yaml`).

When you use `tools/run_simulation.py`, the runner sets
`OT_CONFIG_PATH` for you — you don't need to manage it manually.

### 2. Load labware and validate

For each slot in the config's `labware` map, the protocol calls
`protocol.load_labware(...)`. It then loads the pipette and attaches the
tip rack.

After loading, it runs all seven validation rules from
[configs/SCHEMA.md](../configs/SCHEMA.md). If any rule fails, the
protocol raises an exception with a clear message. No tips are picked up,
no liquids are moved.

### 3. Dilute (slot 1 → slot 2)

For each dilution factor N in the config's `dilutions.factors` list:

1. Compute volumes:
   - `V_stock = final_volume_ul / N` (rounded to 1 decimal)
   - `V_diluent = final_volume_ul − V_stock` (rounded to 1 decimal)
2. Pick the next destination well in slot 2 (column-major order: A1,
   B1, C1, … H1, A2, B2, …).
3. Pick up a fresh tip, transfer `V_diluent` from the reservoir
   (slot 5, well A1) to the destination, drop tip.
4. Pick up a fresh tip, transfer `V_stock` from the sample tube
   (slot 1, well A1) to the destination, mix 5 times at 80% of final
   volume, drop tip.

### 4. Print (slot 2 → slot 3)

For each entry in `paper_print.well_map`:

1. Pick up a fresh tip.
2. Transfer `print_volume_ul` from the source well in slot 2 to the
   matching destination well in slot 3.
3. Drop tip.

## Volume math — worked example

Using the defaults: stock = 1000 µM, final volume = 100 µL, dilutions =
[2, 3, 4, 5, 10].

| Factor (N) | V_stock (µL) | V_diluent (µL) | Result conc (µM) | Dest well |
|-----------|-------------|---------------|------------------|-----------|
| 2 | 50.0 | 50.0 | 500.0 | A1 |
| 3 | 33.3 | 66.7 | 333.33 | B1 |
| 4 | 25.0 | 75.0 | 250.0 | C1 |
| 5 | 20.0 | 80.0 | 200.0 | D1 |
| 10 | 10.0 | 90.0 | 100.0 | E1 |

**Total stock consumed:** 50.0 + 33.3 + 25.0 + 20.0 + 10.0 = **138.3 µL**
(out of 500 µL available).

**Note on the 10x factor:** V_stock = 10.0 µL is below the P300's
minimum reliable volume (~20 µL). The config generator warns about this.
The protocol's validator will raise an error. If you want to include 10x,
consider raising `final_volume_ul` to 200 µL (which gives V_stock =
20 µL for 10x).

## Well assignment order

Wells are assigned in Opentrons column-major order, matching the return
value of `plate.wells()`:

```
A1  A2  A3  ...  A12
B1  B2  B3  ...  B12
C1  C2  ...
...
H1  H2  ...      H12

Iteration order: A1, B1, C1, D1, E1, F1, G1, H1, A2, B2, ...
```

The first dilution factor goes to A1, the second to B1, and so on down
the column before wrapping to A2.

The slot-3 print mapping mirrors this — `paper_print.well_map` is
auto-generated by `tools/make_config.py` to match.

## Why `protocol.comment` instead of Python `logging`?

The protocol uses `protocol.comment(...)` for all output instead of
Python's `logging` module. This is intentional:

- **Separation of concerns.** The protocol runs inside the Opentrons
  simulator, which captures `protocol.comment` output in its transcript.
  Python `logging` would go to stderr and be invisible to the simulator.
- **The runner owns logging.** `tools/run_simulation.py` sets up Python
  `logging`, parses the transcript, and writes the structured log file.
  The protocol just needs to emit tagged messages.
- **Portability.** If you upload the protocol to a real OT-2 via the
  Opentrons App, `protocol.comment` lines appear in the app's run log.
  Python `logging` calls would not.
